# P4.3 - why a GLM serve answer ends with a literal user-turn marker, and why its finish_reason is length

Read-only source analysis plus one config change. Nothing here was built or run by this
analysis: no engine binary, no HIP context. Everything about the GPU comes from what the
operator already witnessed, and each number below names the log it came from.
Written 2026-10-23 in worktree /ai/engines/gfx906/worktrees/xolotl-merge (branch
gfx906/xolotl-merge, HEAD 331cafd4).

## 1. What was witnessed

One GLM serve session on one MI50 (gfx906), started as

        python3 -m serve.server --engine strata --config tools/glm/serve/strata-glm-mayal-gfx906.json --port 8147

(the command in tools/gfx906/run-p4.3-vram-watch.sh line 76; tokenizer dir
/ai/models/tok/glm-5.3-flash, engine wrapper tools/glm/serve/glm-engine-906.sh).
The request was a chat completion, max_tokens 64. The config's thinking budget is 16384
(reasoning_budget_tokens in tools/glm/serve/strata-glm-mayal-gfx906.json), and
serve/server.py:4253-4260 caps it when max_tokens is smaller: reserve =
min(max(ANSWER_RESERVE_MIN, max_new // 4), max_new // 2) with ANSWER_RESERVE_MIN = 512 at :153,
so with max_new 64 the reserve is 32 and the budget becomes 64 - 32 = 32.

The engine's own lines (log /tmp/strata-glm-mayal-906.log, boot at line 151, 08:31:30, the
request after it; the engine had been restarted with --vram-margin 5.0 by the harness copy of
the config, --stop 154820,154827,154829):

        serve: reuse lcp=0 hist=0 snap=-1 prompt=18 -> reused=0
        serve: prompt 18 tokens (0 reused) in 5.19 s = 3.5 tok/s
        serve: 32 tokens in 9.17 s = 3.38 tok/s (cancel)
        serve: reuse lcp=50 hist=50 snap=18 prompt=67 -> reused=50
        serve: prompt 7 tokens (5 reused) in 4.39 s = 3.9 tok/s
        serve: 6 tokens in 1.8 s = 3.2 tok/s (stop)

So the LAST engine segment reported a natural stop after 6 tokens. The server's own line for
the same request (logs/p4.3-vram-serve-20261023-083129.log lines 18-21):

        thinking budget reached (32 tokens): wrapping up the thinking
        thinking: 49 of max 64 tokens, 3.7 tok/s
        answering: 52 of max 64 tokens 3. tok/s
        done: 55 tokens in 2 s (length, cancel=False), expert cache 27.% hit

and the HTTP body the client got (logs/p4.3-vram-serve-20261023-083129.log.curl):

        content: "Hello there, friend!<|user|>"
        finish_reason: "length"
        usage: prompt_tokens 18, completion_tokens 55, total_tokens 73
        timings: predicted_n 55, predicted_per_second 3.5

Two symptoms, which are NOT the same bug and are judged separately below:
(A) finish_reason length although the engine's last segment said stop, and completion_tokens
    55 against a max_tokens of 64.
(B) the assistant's visible content ends with the literal text of a user-turn boundary,
    8 characters, after a coherent answer.

## 2. What the source shows

### 2.1 The token-id stop list the loop consults, and what it holds for this tokenizer

serve/server.py:3220-3221 (Service.__init__) is the only place self.stop_ids is built:

        self.stop_ids = set(tokenizer.encode(IM_END, parse_special=True) +
                            tokenizer.encode("<|endoftext|>", parse_special=True))

IM_END is the Qwen end-of-turn literal (serve/server.py:75). serve/server.py:4409 is the only
reader: for every id the engine streams, if t in self.stop_ids the loop breaks and
finish = "stop" (:4413). When the id is not in that set the same token goes on through
:4415/:4416 (raw_ids, seg) to :4424 (detok.push) and the parser, which is where symptom B comes
from.

The GLM tokenizer dir /ai/models/tok/glm-5.3-flash holds four plain files (chat_template.jinja,
vocab.json 154880 entries, merges.txt, token_type.json 154880 entries). serve/server.py:6946-6954
builds the tokenizer from exactly those three data files (ST.Tokenizer(tokens, merges, types)),
and serve/server.py:7025-7026 takes the chat template from the same dir when it is there.
tools/strata_tokenizer.py:131-141 builds the special-literal map from token_type: type 3
(CONTROL) and type 4 (USER_DEFINED) become literals; encode(..., parse_special=True) matches
all of them (tools/strata_tokenizer.py:327-335).

Read from those files, not guessed (inspect of vocab.json + token_type.json, which is a plain
list of 154880 integers indexed by id; type 1 NORMAL, 3 CONTROL, 4 USER_DEFINED):

        154820  type 3  end-of-text marker
        154827  type 3  user-turn boundary marker
        154828  type 3  assistant-turn boundary marker
        154829  type 3  observation marker
        154841 / 154842  type 4  think open / think close
        154843 / 154844  type 4  tool-call open / close

The ids the GLM engine itself stops on are the same numbers, from the config: the "--stop"
entry in the "args" array of tools/glm/serve/strata-glm-mayal-gfx906.json passes
154820,154827,154829, and tools/glm/glm_generate.cpp:102 parses that option; glm_generate.cpp:730
tests is_stop and :731 ends the generation with finish "stop" when a sampled id is in the list.
bench/glm-2026-10-08/upstream/generation_config.json lists the same three ids as
eos_token_id, which is where the config's numbers came from.

What self.stop_ids therefore holds for this tokenizer dir: both literals the server encodes are
Qwen names, and neither end-of-text nor end-of-turn text exists in the GLM vocab under those
names, so encode() falls through to BPE and yields the ordinary text pieces of those strings,
not one control id. The two Qwen ids 248044 and 248046 are outside this vocabulary entirely
(vocab size 154880), so they can never be sampled. Verdict on task 2 from source: this
model's end-of-text id is 154820 and its user-turn-boundary id is 154827; the ids in EOS_IDS
(server.py:732) could never match this tokenizer, and self.stop_ids at 3220 does not resolve
to them either - unless the GLM shim is loaded, see 2.3.

### 2.2 EOS_IDS: what consumes it, and what it is not

serve/server.py:732 defines EOS_IDS = {248044, 248046} with the comment "the engine's default
--eos-ids". It is a module constant, and only three lines read it, all inside the parallel
(batch-slot) engine path in StrataEngine.generate_batched:

        serve/server.py:1657   the solo leg decides whether to promote into a batch slot
        serve/server.py:1823   a slot's BDONE cancel decides whether to fall back to the solo path
        serve/server.py:1859   the finally block drains a slot's BDONE after an end-of-turn token
        serve/test_parallel.py:805 patches it with a fake id (the only test that touches it)

This request did not go through that path: the config has no "parallel" / --batch key, so
serve/server.py:4309 sets par = False and run() uses the single-turn fifo plus
StrataEngine.generate. So EOS_IDS was not read at all in the witnessed request. It is still
wrong for this model (the same Qwen ids), and it would be wrong on the batch path for GLM.

The engine default EOS_IDS names is real and equally Qwen-only:
src/program/generate.cpp:615-616 (stop_eos = false, eos_ids = {248044, 248046}), --eos-ids
parsed at :2219-2222 which also sets stop_eos, and forced true for serve mode at :2563. That is
the upstream Qwen engine; glm_generate has its own --stop list and no eos default, so the
comment in server.py:732 describes a different engine than the GLM one.

### 2.3 The shim that fixes this exists, and this session did not load it

tools/glm/serve/serve_glm.py is the GLM serve entry the authors wrote. It sets
S.IM_END = "the user-turn marker" (line 48) and wraps Service.__init__ so stop_ids also gains
the ids of the observation, end-of-text and user markers (:49-55, the loop at :52), on top of the
glm4 pre-split (line 37) and GLM's tool-call format (glm_parse_tool_call at :78, the
OutputParser.__init__ wrapper at :123-132). It prints nothing that distinguishes it in the engine
log, so the way to tell which entry a session used is the command line.

The witnessed session used the plain entry, not the shim: tools/gfx906/run-p4.3-vram-watch.sh
line 76 runs python3 -m serve.server --engine strata --config ... (log
logs/p4.3-vram-serve-20261023-083129.log, which is that script's own log file). So the whole
GLM piece of the serve path - tokenizer pre-split, stop ids, tool-call parser - was absent.
This is the single cause of both symptoms; each is traced separately below.

### 2.4 Symptom B: how the user marker reaches the visible text

The engine streams a T line for every sampled token, including the stop one:
glm_generate.cpp:727 prints it, :730 tests is_stop and only then breaks with finish "stop"
(:731). So id 154827 was sent to the server as a token.

serve/server.py:4409 asks whether that id is in self.stop_ids. Without the shim it is not, so
the token is not treated as the end of the turn: :4415 appends it to raw_ids, :4416 to seg, and
:4424 detok.push(t) decodes it. Detokenizer.push uses tools/strata_tokenizer.py:337
(token_bytes), which returns the raw bytes of the token's vocabulary text, so 154827 becomes
the 8 ASCII characters of the user-turn literal (ords 3c 7c 75 73 65 72 7c 3e).

serve/frontend.py is what normally keeps such text out of the answer, and it cannot:
literal_tags / mark_think_literals / unmark_think_literals (serve/frontend.py:258, and the
unmark helper at :365) replace control literals with private marks when RENDERING the prompt
(the tokenizer's special map is built at serve/server.py:6946-6960 and the template is taken from
the tokenizer dir at :7025-7027), so a marker inside a user message cannot open or close a turn.
Nothing in serve/frontend.py un-marks or hides a control literal that appears in the model's
OUTPUT: the content branch of OutputParser.feed (:1247-1285) emits self.buf as content and the
only tag it holds back is the tool-call opener (CALL_START). The OutputParser was built without
any control-literal map at all (serve/server.py:4261, no literals argument), so the marker text
passes through as content.

That is why the answer ends with the literal user-turn text: it is not a decoding artefact and
not a template leak, it is the model's own stop token, streamed as an ordinary token because
the id was not in the server's stop list. With the shim loaded, :4409 would break at the id,
the marker would never reach the detokenizer, and finish would be "stop".

### 2.5 Symptom A: which line set finish to length

finish starts as "length" (serve/server.py:4262) and only these lines change it:

        4413          a stop id (break)                     -> "stop"
        4441          a stop string from the request        -> "stop"
        4469          EngineDied                            -> "error"
        4475          the engine's ERR line                 -> "error"
        4489          EngineSilent on the close             -> "error"
        4514          non-finite logits after some tokens   -> "length"
        4586          a stop string hit inside the wrap-up   -> "stop"
        4590          cancel                                -> "cancel"
        4601          client disconnect                     -> "disconnect"

For the witnessed request the path is the thinking-budget one. serve/server.py:4457-4461 set
wrap = True when thought reaches the budget of 32 (log line "thinking budget reached (32
tokens)"), which breaks out of the token loop; the finally at :4482-4483 closes the engine
generation (gen.close(), the engine's "(cancel)" segment), and :4565-4588 builds the second
pass: REASONING_WRAP_UP (server.py:158) encoded at :4571 and appended to the prompt, then the
outer while at :4435 starts a fresh engine generation with max_new - n tokens left.

The second pass returned 6 ids and its DONE said stop. Two candidates for that:

- The branch near 4536 (reasoning_close_retry) does NOT match: the config has no
  "reasoning_close_retry" key, so self.reasoning_close_retry is False (server.py:3149), and its
  guard also requires finish == "stop" from a stop-id break, which never happened. Neither the
  4536 branch nor the break at 4573 fired: at 4572 the room check (max_new 64 - n 49 -
  len(extra)) was above 1, so 4573 was not reached.
- The stop must therefore have come from the ENGINE's own list: the last of the 6 ids was
  154827 and glm_generate.cpp:730 is_stop(tok) matched the config's --stop, so the engine broke
  with finish "stop" (glm_generate.cpp:731). The engine prints its T line before the stop test
  (:727 prints, :730 tests), so the server saw that id at :4409 first and passed it; its loop
  then ended on the generator's StopIteration with finish still "length" from :4262. The DONE
  the engine wrote for that segment is what its "(stop)" log line reports; the server keeps it
  as a segment for timings (:4491-4493) and never reads its finish for the request's own
  finish_reason.

completion_tokens 55 is the same story in numbers: 32 tokens of thinking + the wrap-up literal,
whose ids are counted at :4577-4578 (n += 1 per id), + 6 from the last pass = 55, below max_new
64, so nothing cut the request for length. "length" here means "the loop ended without
recognising an end of turn", not "the cap was reached".

## 3. Verdict, one symptom at a time

Symptom A - finish_reason "length" while the engine's last segment said stop.
CORRECTNESS. The HTTP answer told the client the reply was cut by the token cap when it was
not: 55 of 64 tokens, and the model had closed its turn. An agent client that keys on
finish_reason will re-ask, truncate, or treat a complete answer as incomplete. The counter that
decided it is serve/server.py:4262 (finish = "length") never being replaced because :4409 did
not recognise the model's end-of-turn id. The engine was right; the server's finish decision
was wrong.

Symptom B - the literal user-turn marker at the end of the visible content.
COSMETIC, and separately fixable. The answer itself was complete and coherent
(logs/p4.3-vram-serve-20261023-083129.log.curl: "Hello there, friend!" is the whole intended
reply, and the marker follows it). What leaked is the 8-character text of the model's own stop
token, which the engine had already announced by its DONE finish "stop". It is a display defect
of the same gap, not a second fault in the engine or a sign that generation ran past the turn:
the engine stopped at that exact token. It stays cosmetic only as long as the marker lands at
the very end; the same gap would leave any mid-reply marker visible too, which is why it should
be fixed by the same change rather than by trimming the tail.

Both trace to one thing: this session ran the plain serve.server entry, so the server's stop list
held Qwen's two literals (serve/server.py:3220-3221) instead of GLM's three ids
(154820, 154827, 154829 - the same list the engine was given in the "args" of
tools/glm/serve/strata-glm-mayal-gfx906.json). EOS_IDS (server.py:732) played no part in
this request; it is a second instance of the same wrong-for-GLM assumption, on the batch path.

## 4. Proposed fix (proposal only - serve/server.py was not edited)

Shape: a per-config list of stop token ids, opt-in, that feeds self.stop_ids. Nothing changes when
the key is absent, so every existing config's behaviour stays byte-identical.

        in the serve config, next to "tokenizer":
            "stop_token_ids": [154820, 154827, 154829]

        in serve/server.py, after line 3221 (Service.__init__), same shape as the other
        opt-in config keys this class already reads:
            for i in (cfg stop ids, read where the Service is built, default empty):
                self.stop_ids.add(i)

Why this shape and not a change to EOS_IDS:

- EOS_IDS is consumed only by the parallel/batch path (server.py:1657, :1823, :1859; the one
  test that touches it, serve/test_parallel.py:805, patches the name). It is a Qwen default
  that names the upstream engine's --eos-ids (src/program/generate.cpp:615-616, :2219-2222).
  Changing the constant would move the batch path for every model, including Qwen, to fix a
  GLM problem, and would not fix the request path at all - the witnessed request never read it.
- self.stop_ids is the only stop list the single-request loop consults (:4409), so a config
  value there is enough for both symptoms: the id breaks the loop, finish becomes "stop"
  (:4413), and the marker never reaches the detokenizer (:4424).
- The config already passes the same ids to the engine via --stop, so the server and engine stop
  on one list read from one place; a validation warning when the config's stop ids and the
  engine's --stop list disagree is the natural companion, and is also opt-in.
- Blast radius of the opt-in key: one read in Service construction, one set update, and the
  finish decision at :4409-:4413. It does not touch EOS_IDS, the batch path, the tokenizer, the
  template, the parser, or any request without the key.
- Alternative considered and rejected as the primary fix: always launch GLM through
  tools/glm/serve/serve_glm.py. That is the authors' shim and it already does this (:48-55),
  but it also swaps the pre-tokenizer and the tool-call parser, so it changes tokenisation of
  every request. It should be the documented entry for GLM (this fork's own P4.5 note reached the
  same conclusion for V4.1 and its shim), but the config key is the minimal, testable change, and
  the two are compatible: the shim, when loaded, still adds the same ids
  (tools/glm/serve/serve_glm.py:49-55).
- Do not fix this by string-trimming the answer's tail: a mid-reply marker would survive it, and
  the finish_reason would stay wrong.

## 5. What remains unproven

- Which id a plain chat reply stops on, read from /ai/models/tok/glm-5.3-flash/chat_template.jinja
  (257 lines): the template opens a turn with the user marker (line 139), the assistant marker
  (line 141), the system marker (line 190) and the observation marker (line 162), and its
  add_generation_prompt tail is the assistant marker plus the think opener (lines 255-256). It
  never writes the end-of-text marker. So a reply ends when the model itself emits the next turn
  marker, and the id seen in the witnessed answer (the user marker) is what the template's own
  convention predicts - but the model's learned behaviour, not the template, decides which of
  154820 / 154827 / 154829 comes first, and one answer is not a rate. All three belong in the
  stop list, which is what the engine is already given.
- The exact token count of the wrap-up literal with the GLM tokenizer (17 = 55 - 32 - 6, from
  the witnessed numbers, not from an encode). Note that REASONING_WRAP_UP at serve/server.py:158
  is 62 characters and ends with a think-close literal, so a GLM encode of it is a cheap check
  of that 17 - and the engine's own line for the second pass (prompt 67, reused 50) is
  consistent with 18 + 32 + 17 = 67, which is arithmetic on witnessed numbers, not a measure.
- The self.stop_ids contents at runtime for this tokenizer dir: derived from
  tools/strata_tokenizer.py:131-141 and :327-335 by reading the four plain tokenizer files, not
  by running the tokenizer in a live server. A one-line print under the mock engine (no GPU)
  would turn that from reading into measurement.
- Whether the same finish_reason defect appears on the batch path for GLM: this box ran the
  single-request path only, and the batch path's own end-of-turn test (server.py:1657, :1823,
  :1859) was never exercised with a GLM id.
- The margin change in tools/glm/serve/strata-glm-mayal-gfx906.json is section 6's evidence
  (#32), not this stop-token analysis; the two are recorded in the same edit and are independent.

## 6. The two numbers the config comment cites, re-derived from this box's logs

Recorded here because the config change in this same worktree cites them, and one of them does
not survive arithmetic.

The refused allocation: exact. The ASan line in /tmp/strata-glm-mayal-906.log (line 104) names
0x2404800 = 37767168 bytes = 36.02 MiB. mmq::q8_bytes(cap, cols) with the mmq block type
(128 bytes of qs plus 4 half2 scales = 144 bytes per 128 values, 512-padded columns, plus 128
spare blocks; tools/ds4/ds4_moe.cpp m_g/m_u/m_d allocations) gives 37767168 for cap 16384,
cols 2048 to within 8 KiB, and no other (rows, cols) in that neighbourhood lands as close. So
the refusal is one q8 buffer of the MMQ scratch set at the 16384-row cap, which is what the
issue says.

The 2.57 GiB burst: not reproduced by this arithmetic, and the config comment now says so.
Adding the set the code allocates at that cap - m_gu 256 MiB, m_h 128 MiB, m_g + m_u + m_d
3 x 36.02 MiB, m_bnd 2 KiB, m_iota 64 KiB - is 492 MiB, and the c_stage pair (2 x max(1024 MiB,
blob)) is 2.002 GiB at the 1 GiB floor, so the visible total is about 2.49 GiB, not 2.57 GiB.
The 2.57 GiB figure in the issue came from the shape of the VRAM curve, and the m_* set plus
m_xd and the c_stage pair are the same order, so the workaround stands on its own: the refusal
is arithmetic-exact and the free space at margin 4.0 is smaller than the set the first MMQ run
asks for. What is NOT settled is the size of the set (this arithmetic says ~2.5 GiB, the curve
witness said 2.57 GiB, and the difference is roughly the m_iota + m_bnd + m_xd tail), and
whether margin 5.0 is enough on a box with a different expert-slot layout. The curve at 5.0 on
this box has since been witnessed (same log, boot 2026-10-23 08:31:38, lines 151-172: slots auto
18.89 GiB of expert slots at margin 5.00 against 19.89 at margin 4.00, and the budget-cancel
request completing through its wrap-up prefill with no m_xd refusal), so the workaround is
measured green here; what that witness does not settle is the size of the set, and the same run
is the source of the finish_reason defect analysed above.
